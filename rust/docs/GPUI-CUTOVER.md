# GPUI-CE production cutover

The acceptance target is the installed LuxuryGram client, not the `luxurygram-shell` preview. Keep the current client usable until its replacement passes the same scenarios. A build that still uses Qt for the engine is a migration build, not a Qt-free release.

## Integrating the live chat first

- Reuse the authenticated C++ model initially. The Qt `ChatWidget` already subscribes to [`Data::HistoryMessagesViewer`](../../Telegram/SourceFiles/data/data_history_messages.cpp#L467) in its [list source](../../Telegram/SourceFiles/history/view/history_view_chat_section.cpp#L5296). The viewer merges migrated history, reconciles pending IDs, reacts to index invalidation and requests missing pages through [`ApiWrap::requestHistory`](../../Telegram/SourceFiles/apiwrap.cpp#L3782). Do not create a parallel history RPC, database reader or protocol stack for the new renderer.
- Subscribe at the session boundary, not inside a Qt widget. Project owned values keyed by account and the full message ID (peer and message), and consume message-change notifications as well as slice changes: replacing text does not necessarily change a slice of IDs. Required regression cases: pagination with scroll anchor preserved, message edit/delete, pending ID replaced by server ID, and migrated history with equal numeric IDs from different peers.
- Clear the view and invalidate queued work on account/chat switch, passcode lock and logout. An account may remain alive after switching, so weak pointers alone do not reject stale deliveries. Do not extend the existing local automation socket to carry chat content. Validate with the [Test-session fixtures](../../Telegram/SourceFiles/test/README.md), without a real user profile or transcript in logs.

[`Data::HistoryTextViewer`](../../Telegram/SourceFiles/data/data_history_messages.cpp#L621) projects the existing model stream into owned UTF-8 text rows with full message IDs and page counts. It skips service, sponsored, protected, timed, media-bearing, and spoiler messages. The projection checks protection on both the selected chat and the source peer of each row, including migrated messages, and schedules a fresh snapshot when either peer's protection changes. The receiver must evict any cached or queued rows when permissions change; the full cross-thread revocation path is not implemented yet. It requests a refresh on edits and ID changes of rows in the current slice, using the same guarded main-thread scheduling as the underlying viewer. A text snapshot now carries the ordered old and new full IDs observed since the previous delivered snapshot, even when several events share one scheduled refresh. The existing ID-only viewer does not emit this metadata. The translation unit compiled to an object with MSVC using compiler settings from the generated Windows Debug project; these events have not been verified in a running session.

The [GPUI feed](../apps/luxurygram-shell/src/feed.rs) replaces its visible snapshot without jumping away from a retained scroll anchor, and rejects updates from revoked subscriptions. The receiver keys rows by peer and signed message number, matching both fields of `FullMsgId`; a GPUI regression verifies that prepending a migrated page while changing the anchored row's ID preserves the anchored row and pixel offset, even when another peer has its old message number. The [history bridge](../apps/luxurygram-shell/src/history_bridge.rs) is the production C ABI: `luxurygram_history_start` opens the feed on its own GPUI thread, `luxurygram_history_apply` delivers an owned snapshot with its ordered rekeys, `luxurygram_history_clear` revokes it and also drops every snapshot already queued, `luxurygram_history_visible_count` reports the applied row count, and `luxurygram_history_window` returns the feed's HWND (0 once the window closed). The feed starts empty; the synthetic demo rows are not reachable through the bridge. The opt-in [Windows C++ test host](../../tools/tests/gpui_windows_host_smoke.cpp) runs a Qt Core loop on the main thread while the bridge runs on its own thread in the same process. The observed run reported malformed UTF-8 rejected with code 2, a two-row snapshot with one rekey accepted, the feed holding two rows, a clear bringing it back to zero, the exported handle equal to the window found by title, a cross-thread `SetWindowPos` placing that window at an exact 120,140 700x480 rectangle, `SW_HIDE` and `SW_SHOWNOACTIVATE` from the Qt thread taking effect, the handle cleared after close, 42 Qt timer ticks and host exit code 0. `ShowWindow` reports the previous visibility, so only the resulting `IsWindowVisible` state is a valid check. The DLL imports `TaskDialogIndirect`, so the host needs a Common Controls v6 manifest; a host without it fails to load the DLL at all. This proves the ABI, threading, placement and revocation contract, not that text was painted, and it passes no account data. The C++ producer emits a null snapshot when the passcode, setup-email, screen or terms lock engages or a different session becomes active; [an isolated RPL check](../../tools/tests/history_revocation_rpl.cpp) compiled with MSVC and confirmed that all five revocation causes stop the stream and suppress later rows. The Qt client subscribes to this producer through [`HistoryView::ShowGpuiHistory`](../../Telegram/SourceFiles/history/view/history_view_gpui_bridge.cpp), called from the [`ChatWidget` constructor](../../Telegram/SourceFiles/history/view/history_view_chat_section.cpp) with a lifetime the widget owns, so switching chats destroys the subscription. The bridge loads `luxurygram_shell.dll` from the application directory when present and does nothing when it is absent; a null snapshot calls `luxurygram_history_clear`. `HistoryView::GpuiHistorySurface` in the same file keeps the feed window exactly over the chat area's viewport: gpui-ce 0.3.0 creates only top-level windows (`WindowKind` is `Normal`, `PopUp`, a parent-anchored popup or `Dialog`; there is no child or owned HWND and no public `set_bounds`), so the surface tracks the viewport with `SetWindowPos` on every move, resize, show, hide or window-state change through `base::install_event_filter`, hides when the host window is hidden or minimized, and the most recently shown `ChatWidget` alone owns the single feed window. While the surface is active the Qt message list is hidden; release on destruction hides the feed and clears it. Both translation units compiled to objects with MSVC using the generated Qt 6.11.2 Windows Debug project settings, and the full Debug build of `Telegram` reached the link of `LuxuryGram.exe` with them. No running session has delivered a real snapshot through this path yet: the machine has no golden portable test account, so the live-history, lock and chat-switch behaviour of the surface is still unverified in a running client.

Reproduce the bridge check on Windows x64: from `rust/`, run `cargo rustc --offline --locked -p luxurygram-shell --lib --crate-type cdylib`. In an x64 Visual Studio developer prompt, create and enter `out\gpui-qtcore-smoke`, then run `qmake ..\..\tools\tests\gpui_windows_host_smoke.pro` with the prepared Qt installation, followed by `nmake`. Launch the resulting test host with the absolute path of the Debug `luxurygram_shell.dll`. It starts the feed from the main thread, applies a two-row snapshot with a rekey, clears it, checks the exported handle, moves and toggles the feed window from the Qt thread, and exits with 0 only when bad input was rejected, both counts were observed, the handle matched, the geometry and visibility took, the Qt timer ran, the handle cleared and the GPUI window closed.

## Shipping the bridge in the build

The DLL is a prepared third-party product like `tdesktop_rust`, not a CMake target: the `luxurygram_shell` stage in [`prepare.py`](../../Telegram/build/prepare/prepare.py) runs `cargo rustc --locked -p luxurygram-shell --release -Z build-std=std,panic_abort --target x86_64-win7-windows-msvc` with `+crt-static` and the same release profile as `tdesktop_rust`, so it shares the client's CRT model, and copies it to `Libraries/win64/luxurygram_shell/out/`. The win7 target ships no prebuilt standard library, so the stage builds `std` from the `rust-src` component the `rust` stage installs, exactly as `tdesktop_rust` does; without `-Z build-std` cargo would try to download a target instead of compiling. The stage runs from `Libraries/win64`, not from the repository, so it addresses the crate through `scriptPath`, and its version hashes `Cargo.lock`, the crate's `Cargo.toml` and every `src/*.rs`, so any change to the bridge rebuilds it. [`cmake/external/luxurygram_shell`](../../cmake/external/luxurygram_shell/CMakeLists.txt) only names that file through the `LUXURYGRAM_SHELL_DLL` target property (an `INTERFACE` target without `init_target`, which would add compile features an interface cannot carry), and [`Telegram/CMakeLists.txt`](../../Telegram/CMakeLists.txt) copies it beside `Telegram.exe` after the build with `copy_if_different`. The DLL is never linked: it carries its own Rust runtime, which must not sit beside the one inside `tdesktop_rust`. Both configure branches were checked: with the DLL present the generated `Telegram.vcxproj` carries the copy step, and when the stage has not run configure reports that the GPUI chat surface stays off, the copy step is absent and the client is unchanged. A full Debug build of `Telegram` with the bridge linked completed with exit 0, and the client started in a fresh `-workdir` sandbox with the DLL beside the executable, ran for 25 s through the welcome screen and an MTProto WebSocket connection, and logged `Windows Hello availability` normally, so the SDK guard did not break the Hello path. No chat was open in that run, so the bridge was not loaded there; the live chat path is still unverified.

The feed has a composer of its own, hidden until a send handler is installed. `Enter` hands the trimmed text to `luxurygram_history_set_send_callback`, and `HistoryView::EnableGpuiCompose` lets the client install one that marshals the text to the main thread and calls the shown `ChatWidget`'s own `sendTextWithTags`, so permissions, slow mode, scheduled and ephemeral handling and the local message stay the client's. The composer keeps its draft when no callback is installed or the callback refuses. The client does not install the handler yet: the Qt compose area is still the complete composer (IME, emoji, attachments, replies, editing), and two composers on one chat would be a defect, so the feed's composer stays hidden until the compose area is ported. The key path is covered at both levels all the same: a GPUI `TestApp` test drives `h i enter` through `dispatch_keystroke` and the real focus path, and the Win32 host test installs a callback, posts `WM_KEYDOWN` to the real HWND and sees the callback receive the two typed characters. The host test posts asynchronously because GPUI does not run its focus dispatch for a synchronous cross-thread `SendMessage`, and it does not compare the letters because `ToUnicode` yields the host's active keyboard layout.

## Removing Qt, not just widgets

The [production target](../../Telegram/CMakeLists.txt#L82) links both Qt and Qt static plugins. A second constraint comes from the pinned `gpui-ce` 0.3.0 itself: on Windows it creates only top-level windows (`WindowKind` is `Normal`, `PopUp`, a parent-anchored popup or `Dialog`; `WS_CHILD`, an owned HWND and a public `set_bounds` are absent), so a GPUI view cannot be a child of a Qt widget. Until the Qt main loop is gone, the only honest embedding is the one the bridge uses: a top-level GPUI window moved over the chat area by its Qt host. Ending Qt ownership of the main loop is therefore the prerequisite for a real in-window GPUI surface, and not a styling detail. Engine work remains even after stopping Qt painting:

| Boundary | Current production dependency to remove or replace |
| --- | --- |
| Startup and OS lifecycle | [`Sandbox`](../../Telegram/SourceFiles/core/sandbox.cpp#L117) owns `QApplication`, the event loop, the lock and local single-instance socket. Preserve single-instance and deep-link behavior. On Windows, pinned `gpui_ce_platform` 0.3.0 `Platform::run` always owns a Win32 `GetMessageW` loop; `run_embedded` only returns an `ApplicationHandle` after that loop ends, so it cannot host GPUI inside Qt's loop in one thread. The verified coexistence runs GPUI on its own thread. Ending Qt ownership of the main loop remains an engine prerequisite. |
| Account and profile storage | [`Main::Account`](../../Telegram/SourceFiles/main/main_account.cpp#L295) and the [storage domain](../../Telegram/SourceFiles/storage/storage_domain.cpp#L133) use versioned Qt streams. Prove compatibility with disposable copies and retain encrypted, atomic writes and restart behavior. |
| Network and updates | [MTProto TCP](../../Telegram/SourceFiles/mtproto/details/mtproto_tcp_socket.h#L35), [WebSocket](../../Telegram/SourceFiles/mtproto/details/mtproto_websocket_socket.h#L59), [HTTP](../../Telegram/SourceFiles/mtproto/connection_http.h#L59), and the [updater checker](../../Telegram/SourceFiles/core/update_checker.cpp#L170) use Qt networking. Preserve proxy, reconnect, certificate and update verification behavior; see ADR-004 before introducing network/crypto dependencies. |
| Calls and media | [WebRTC bridge linkage](../../Telegram/lib_webrtc/CMakeLists.txt#L82) still pulls Qt. Validate devices, playback/capture, screen sharing and both call types. |
| Remaining UI | Replace dialogs and search, rich messages and media, settings and authentication, calls, Premium/Stars/wallet and LuxuryGram-specific surfaces. The GPUI composer is a first slice: single-line text typed as `key_char` and sent on Enter. IME composition (GPUI delivers it through the platform input handler, not `KeyDownEvent`), paste, emoji, replies, editing, attachments, drafts and the send menu still live in the Qt compose area and are unported. Validate keyboard, screen reader, IME, localization, theming, notifications and platform integration. |

## Release evidence

The full Qt 6.11.2 Windows Debug baseline is built: `cmake --build out --config Debug --target Telegram` completed with exit 0 and produced `out/Debug/LuxuryGram.exe` with the history bridge and the `GpuiHistorySurface` linked in. The local SDK blocker is resolved at the source: `IKeyCredentialWithWindow` and `KeyCredentialManager::RequestCreateForWindowAsync` are absent from the Windows SDK 10.0.26100 revision installed here (contract `UniversalApiContract` 19.0, three `impl/Windows.Security.Credentials.N.h` parts) and present on the CI runner's newer revision of the same SDK number, so `wallet_protection_win.cpp` now guards the owned overloads with `__has_include(<winrt/impl/Windows.Security.Credentials.3.h>)` and a preprocessor block; a `requires` probe cannot detect a missing declaration, and `if constexpr` still requires every name in the discarded branch. On an older SDK the build compiles the unowned ask, which is what an older Windows runs anyway. The owned path is unchanged where the SDK provides it.

On Windows with the CMake Visual Studio generator, run `python -B tools/tests/check_windows_qt_link_inputs.py out/Telegram/Telegram.vcxproj` from the repository root. Exit `1` means a recognized direct Qt input was found; exit `2` means the project could not be inspected; exit `0` clears only this preliminary check. Run against the built Qt 6 Debug project it exits `1` and names `Qt6Cored.lib`, `Qt6Guid.lib`, `Qt6Widgetsd.lib`, `Qt6Networkd.lib`, `Qt6Svgd.lib`, `Qt6OpenGLd.lib`, `Qt6OpenGLWidgetsd.lib`, `Qt6EntryPointd.lib`, the four `Qt6Bundled*d.lib` libraries and the static-plugin inputs (`external_qt_static_plugins_kimageformats.lib` and its `init.obj` among them). That is the current, correct negative control for a migration build: the client is not Qt-free while any of those is a direct input.

For each supported OS and architecture, verify the Debug production target and the actual packaged entry point, native helpers and libraries. Keep package hashes, build identity, compiler/linker inputs and linker maps. Inspect dynamic dependencies (including delay loads) and runtime module/child-process loads on a clean host. Dynamic imports alone cannot rule out Qt: the [native Qt link configuration](../../cmake/external/qt/CMakeLists.txt#L90) explicitly supplies static libraries. Require a known static Qt build to fail the check, and do not count a missing map, absent package member inventory or an untested platform as a pass.

Run end-to-end parity scenarios against disposable profiles: fresh and existing account login, lock/unlock and switch, chat read/search/send/edit/delete, attachments and calls, settings persistence, notifications, deep links, restart and update verification. The cutover requires these checks and a Qt-free installed package, not a successful preview launch.
